Kernel-only conclusions

  • The kernel is at dg parity ≤128 tok/rank (0.97–1.04×) and wins outright ≥512 (0.94× → 0.64× at 8k). The only kernel-level slowdown was a hump peaked at 256 tok/rank (+21%) — now resolved as a knob-bucket artifact (section 2).
  • Hump resolution:jobs 2359949 + 2360287 the 256-max-token knob bucket defaults to epi_warps token-back, whose combine STG (fc2_store_combine, epilogue_refactor.py:2349) misbehaves at that pool geometry (69 µs @256 vs 29 µs @384, non-monotonic ⇒ config artifact). Switching the bucket to standalone_warps (autotune's winner, then pinned + reproduced) gives 248.8 → 232.5 µs and drops epi_fc2 71 → 33 µs. MEGA_IKR=1 is ruled out (worse everywhere, +12–16%).
  • The remaining gap is the serial barrier tail, not compute.job 2360287 With tuned knobs at 256 the compute pipeline (sched/TMA/MMA/epilogue loop totals) finishes at ~190–195 µs — below dg's 205.9 total — but the kernel runs to 234 µs: ~40 µs of serialized cross-rank sync per launch (Tail.NvlinkDrain 16.5 µs token_comm.py:1865 + Tail.NvlinkPublish 7.3 µs :1931 + token-back drain, plus Dispatch_Barrier 15.1 µs :1613 up front). That ≈ the whole +12.9% residual, and the same fixed costs set the absolute floor at 8–128 tok/rank.
  • Action items: (1) knob table: standalone_warps for the 256 bucket + re-sweep (banked, ~16 µs); (2) fold/elide the NVLink drain+publish pair or overlap the tail with the next layer's dispatch (~24 µs/launch at every size); (3) overlap the dispatch count-exchange (~14 µs) with input staging; (4) do NOT pursue IKR here.
  • Exonerated: mma_fc1 ~60–70 µs is the fc1 weight-streaming floor both backends share (kernel_fc12.py:2324); sched_publish (~50%) and epi_fc1_wait (~44%) are pacing symptoms of it; Sched_PreInit_Wait ≈ 0.

3 · Phase flow through the megakernel

One launch = one MoE layer. A token's journey: it is pulled to whichever rank owns its experts, run through fc1 → SwiGLU → fc2 there, and pushed back home. The phases below are the stations along that path, in causal order (marker names in code; every arrow is a producer→consumer handoff that the wait slots measure):

  1. Prologue — pipeline_init_wait: cluster-wide rendezvous, SMEM/TMEM pipelines armed. Negligible.
  2. Dispatch, count exchange — Dispatch_Prep: dispatch warps scan the local top-k table and count how many tokens go to each expert. Dispatch_Barrier: all 8 ranks exchange those counts over NVLink — after this, every rank knows exactly how many rows it will receive per local expert. First cross-rank sync point.
  3. Dispatch, token pull — Dispatch_Pull: for each assigned token, read its NVFP4 data + scale factors + top-k weight from the home rank's symmetric buffer and write it into the local input pool; bump that tile's fc1_ready counter. Runs continuously, overlapped with everything below.
  4. Scheduler — Sched_PreInit_Wait: waits for step 2's counts (measured ≈ 0 — dispatch is never the straggler). Then turns per-expert row counts into work tiles and sched_publish-es them into a small queue; a full queue (consumers busy) shows up as publish backpressure.
  5. TMA loads — tma_weight_fc1/fc2 (A-side): stream expert weights from HBM to SMEM — at low tokens this is the floor, since every expert's full weights move regardless of token count. tma_token_fc1 (B-side): load the tile's tokens from the pool; tma_token_fc1_wait spins until step 3 has delivered them. tma_token_fc2_wait later spins on fc1 output readiness.
  6. MMA — mma_fc1: gate+up GEMM into tensor memory. mma_fc2: down-projection GEMM. mma_acquire covers grabbing input/accumulator slots.
  7. fc1 epilogue — fc1_epi_wait then fc1_epi: read the fc1 accumulator, apply SwiGLU, re-quantize to NVFP4, store to the intermediate workspace and signal fc1_done — which releases step 5's fc2 B-side load.
  8. fc2 epilogue + combine — fc2_epi_wait then fc2_epi: read the fc2 accumulator, scale, and write the result back to the token's home rank. In the default epi_warps mode that cross-rank store is fc2_store_combine inside this phase; in standalone_warps/reuse_dispatch_warps the epilogue stores locally and dedicated warps do the push (token_back_push / Token_Back_By_Push*). epi_flag publishes per-expert done counters that the token-back push consumes.
  9. Kernel tail — Tail.Rendezvous: all 12 warps meet. Tail.NvlinkDrain: cross-rank barrier guaranteeing every rank's combine stores/pushes have landed. Tail.SharedReset + Tail.NvlinkPublish + Tail.LocalReset: zero the launch counters and publish the zeros so the next layer can relaunch immediately. Serial, fixed cost — the residual-gap culprit.

Steps 3–8 all run concurrently on their own warps; the chart in section 4 shows how much of the kernel each station spends working vs waiting on its upstream.

4 · Where kernel time goes (rank 0, phase timing)

The mega kernel is one fused launch that does the whole MoE layer: tokens are exchanged between GPUs, run through both expert GEMMs, and combined back — with no separate kernels in between. Inside each CTA, 12 warps are split into five specialized roles that form a pipeline:

rolewarpsjob
dispatchw8–11pull this rank's share of tokens from all peers over NVLink into the local pool
schedw7turn arrived tokens into work tiles and hand them to the consumers
TMA A/Bw5–6stream expert weights (A) and token activations (B) into shared memory
MMAw4run the fc1 and fc2 tensor-core GEMMs
epiloguew0–3SwiGLU + re-quantize after fc1; after fc2, store results back to the token's home rank (the combine)

How to read the chart: each phase is measured on its role’s own clock (a %clock64 range around the same code the IKET markers wrap). Roles run concurrently, so phases overlap in time and do not sum to the kernel total. Bars are shown as % of that case’s kernel time so the four columns are directly comparable; blue = work, orange = waiting. The upper rows are real work, the lower rows are waiting — and waits are mirrors: a large epi_fc1_wait means mma_fc1 upstream is the pacer, a large sched_publish means the consumers downstream aren’t draining tiles. So compare the work rows across colors first; the wait rows explain who was pacing whom.

All four cases share the same overall shape — a persistent, wait-dominated kernel where sched_publish and the idle/wait slots are always ~40–55% — so the chart in this section plots every case side by side on a common % of kernel time scale, with phases in a fixed order. What differs between cases is which bars move:

  • fixed costs amortize: tail NVLink barriers 15% → 1.5% and dispatch_barrier 7% → 1.3% across 8 → 8k — they only matter on the left of the chart;
  • combine STG (epi_fc2 work) is ~9–13% everywhere except a spike to 28% in the 256-default column (the hump), which the tuned knobs flatten to 5.5% — then it grows back honestly with tokens to ~21% at 8k;
  • per-token work takes over on the right: dispatch_pull 2% → 31%, epilogue work 6% → 37% combined, GEMMs 40% → 34% (of a 10× larger kernel);
  • GEMM µs barely move 8 → 128 (51 → 58 µs fc1: the weight-streaming floor) — the kernel only starts scaling with tokens past ~512.

What goes wrong at low tokens/rank (the highlighted bands)

  • ① The fc1 weight stream is the pacer (yellow band, mma_fc1 row). Every launch must stream all 32 local experts' full fc1 weights from HBM no matter how few tokens arrived, so mma_fc1 is essentially constant — 51 µs at 8 tokens, 58 µs at 128 — and the kernel cannot go faster than this floor. This is why kernel time barely moves from 8 → 128 tok/rank (173 → 200 µs), and why dg is no faster here: it pays the same weights-from-HBM bill.
  • ② The serial barrier floor rides on top (yellow band, dispatch_barrier + tail NVLink rows). ~14 µs of all-rank count exchange at the start plus ~25 µs of NVLink drain/publish quiesce at the end — ~40 µs of pure synchronization per launch, 23% of an 8-token kernel. It is invariant with tokens, so it vanishes by 8k (1.5%), but at decode sizes it is the single biggest non-productive slice after the weight stream. This is the kernel-side optimization target (fold/overlap the tail).
  • ③ Everything else just waits (gray band, the three big wait rows). epi_fc1_wait (~48%), mma consume_work (~51%), and sched_publish (~53%) look alarming, but they are the same stall seen from downstream warps: the epilogue waits on the MMA, the MMA waits on tiles, the scheduler waits on consumers — all ultimately pacing on ①. They are symptoms; fixing them directly wins nothing.
  • Net effect: at 8 tok/rank the kernel runs 173 µs of which only ~70 µs is GEMM math and ~26 µs is epilogue/dispatch work — the rest is the weight-stream floor's slack plus the ~40 µs barrier floor. Lower absolute decode latency therefore comes from ② (barrier fold/overlap) and, more radically, from attacking ① (e.g., weight residency across layers) — not from making the GEMMs or epilogues faster.

5 · Deferred: e2e / barrier-cold behavior (not kernel)

  • e2e (barrier-cold full FI forward) runs 1.19–1.36× at 8–256 tok/rank, crossing below 1.0 between 512 and 1024 — a constant ~40–60 µs/launch cost dg does not pay (dg e2e−kernel ≈ 8–25 µs; cutedsl ≈ 48–87 µs, roughly constant through 8k).
  • Mechanism proof (job 2359944, e2e mode + phase timing): at 8 tok/rank Dispatch_Barrier inflates 14 µs → 164 µs (75% of kernel) on rank 0 — per-rank host launch jitter is absorbed at the first cross-rank sync point.
